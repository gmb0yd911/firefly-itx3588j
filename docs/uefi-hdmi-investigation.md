## Observations

SSH to `firefly` connects as `alarm` to `192.168.4.217`. On the investigating
host, use `ssh -F ~/.ssh/config firefly` to avoid an unrelated system SSH
configuration permissions error.

The running kernel is `6.1.115-vendor-rk35xx`. `bootctl status` identifies the
active entry as `3-6.1-headless-fallback.conf`. This entry uses the firmware DT,
not `/boot/dtb/itx-3588j-uefi.dtb`. The user reports that the vendor entry loses
display immediately or stops the machine. A working SD-card install is available.

Both `fed60000.hdmiphy` and `fed70000.hdmiphy` fail to register their clock
with error `-12`. HDMI controllers and `display-subsystem` remain deferred,
waiting for supplier `clk-port`. `/sys/class/drm` has no display connectors;
the sole card is the NPU. The display manager repeatedly fails to start.

The firmware DT puts each HDMI clock provider in a `clk-port` child node,
without `clock-output-names` on the PHY. The vendor DT and vendor PHY driver
expect the provider on the PHY itself, with names `clk_hdmiphy_pixel0` and
`clk_hdmiphy_pixel1`. The driver reads `clock-output-names` into its clock
registration structure. This mismatch explains the observed clock failures;
it does not establish that repairing them is sufficient for HDMI.

Driver reference:
https://github.com/armbian/linux-rockchip/blob/rk-6.1-rkr5.1/drivers/phy/rockchip/phy-rockchip-samsung-hdptx-hdmi.c

The existing vendor-entry DT also changes power domains to always-on, adds
VOP clocks, and splits HDMI register ranges. Those changes are excluded from
the proposed first test so their effects can be distinguished.

the clock-provider phandle, updates the HDMI PHY references, and removes
current-boot `/chosen` data for the EFI stub to regenerate. Other hardware

## Manual clock-test boot result

The user manually selected the clock test. The board panicked and returned
to fallback. The recovered `dmesg-ramoops-0` establishes that the test kernel
did execute (its command line includes `panic=10`). Both HDMI PHYs reported
`hdptx phy init success`; the clock-binding correction therefore worked.

The next failure was `Kernel panic - not syncing: Asynchronous SError
Interrupt`, during deferred DRM component binding. The trace includes:

```
regmap_write
hdmi_writel
dw_hdmi_qp_bind+0x34c/0xa28
dw_hdmi_rockchip_bind
component_bind_all
rockchip_drm_bind
```

Immediately before the panic, VOP bound and `fde80000.hdmi` began binding.
This is evidence of a controller-register bus fault, not another missing
clock-provider failure. The asynchronous exception does not by itself prove
which register access or power/clock/reset state caused it. Controller
initialization and the known-working SD-card BSP need comparison before
choosing the next change.

Crash logs were copied to `/tmp/firefly-clocks-panic.log` and
`/tmp/firefly-clocks-console.log` on the investigating workstation. The board
is currently back on headless fallback with SSH available.

### Desktop confirmed; connected-boot clock-hold test prepared

The user reconnected HDMI and confirmed a desktop. DRM state independently
confirms HDMI-A-1 connected/enabled, VP0 active, 2560x1440p60 with a
241.5 MHz pixel clock. Captured as
`~/.local/state/firefly-hdmi/desktop-confirmed.json` on the workstation.

The remaining problem is booting with HDMI already connected. A separate
experimental DTB adds seven `regulator-fixed-clock` always-on consumers for
the VOP clocks, using the mechanism and clock set from v1.1 firmware's
`FdtFixupVopDevices()`: ACLK/HCLK VOP, four VP pixel clocks and PCLK VOP.
Unlike the firmware's forced-GOP mode, this tree retains all native DRM
nodes. Keeping explicit clock references may prevent a warm-handoff clock
transition that `clk_ignore_unused` cannot prevent. This remains a hypothesis
until hardware testing; it is not a confirmed connected-boot fix.

`scripts/build-uefi-clock-hold-dtb.sh INPUT OUTPUT` builds the experimental
tree from the SD BSP DTB. Shell syntax passes, decompilation succeeds, and
the diff contains only the seven new clock consumers. VOP clock IDs are
derived from its existing clock names/specifiers rather than assuming a
different kernel's IDs. The script neither installs nor activates a boot.
